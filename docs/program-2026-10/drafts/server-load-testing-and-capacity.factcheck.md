## Teaching issues

1. The "Protocol-level bots" row says these bots "send inputs at the real tick rate" and then cites Riot's 10,000 per process. Riot's harness drove platform calls (party, matchmaking, store, loadout) and connected to a mock game server that "did nothing". It did not send gameplay inputs at tick rate. Reword to "Riot's platform harness, which made service calls rather than gameplay inputs, ran about 10,000 simulated players per process on four CPUs." Otherwise readers will budget thousands of tick-rate input streams per core on Riot's authority.
2. The Full-jitter `cost` field says the first retries "are not spread evenly in time". Full jitter is uniform over [0, cap], so within each window the retries are spread evenly. The real cost, which motivates Equal Jitter in the AWS post, is that some sleeps are very short. Fix: "some clients retry almost at once, which a slow-to-recover service still feels; equal jitter keeps a minimum wait at the cost of longer completion."
3. Unity pitfall: "Sharing one System.Random across threads ... so the jitter is identical". Microsoft documents Random as not thread-safe. Concurrent use corrupts its state, and it can then return 0 repeatedly. The result is broken jitter (all zeros), not identical jitter. Reword to "corrupts it so it returns zeros, and every bot retries at once".
4. Players-per-core in how[7] treats the cost per player as constant. Per-player cost rises with room size because of interest management, and the draft warns against linear extrapolation elsewhere. Add "measured at the target room size".
5. Interview mid[0] follow-up, "How long until the queue is unbounded": with a pool of 200 and 10 s holds, service caps at 20/s against 50/s arrivals, so the queue grows by 30/s and never drains. The question invites a wrong "time to" answer. Consider "How fast does the queue grow, and what should the service do?"
