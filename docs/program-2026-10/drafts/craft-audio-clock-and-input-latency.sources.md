## Engine documentation
- Godot sync recipes (system clock drifts: "sound hardware clock is never exactly in sync with the system clock"; hardware method = playback position + get_time_since_last_mix - get_output_latency; discard decreasing values because of multi-threading). https://docs.godotengine.org/en/stable/tutorials/audio/sync_with_audio.html (read)
- Godot AudioStreamPlayer.get_playback_position: not always accurate because the server does not mix every frame; add get_time_since_last_mix. https://docs.godotengine.org/en/stable/classes/class_audiostreamplayer.html (read)
- Godot AudioServer: get_output_latency "based on audio/driver/output_latency, exact value differs by OS and driver", can be expensive, do not call every frame; get_time_since_last_mix; get_time_to_next_mix. https://docs.godotengine.org/en/stable/classes/class_audioserver.html (read)
- Godot ProjectSettings audio/driver/mix_rate 44100, audio/driver/output_latency 15 (unit, milliseconds, is my reading; the class page gave no description). https://docs.godotengine.org/en/stable/classes/class_projectsettings.html (read)
- Godot InputEvent has one property, device, no timestamp. https://docs.godotengine.org/en/stable/classes/class_inputevent.html (read). Input.use_accumulated_input default true, merges similar events per rendered frame. https://docs.godotengine.org/en/stable/classes/class_input.html (read)
- Godot physics default 60 iterations per second; use delta. https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html (read)
- Unity AudioSettings.dspTime: seconds, based on the samples processed, "much more precise than Time.time". https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSettings-dspTime.html (read)
- Unity PlayScheduled advises scheduling 100 to 200 ms ahead: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSource.PlayScheduled.html (taken from the sibling rhythm draft's sources, read there; not re-fetched here)
- Unity Audio settings: DSP Buffer Size options Default, Best Latency, Good Latency, Best Performance. https://docs.unity3d.com/6000.0/Documentation/Manual/class-AudioManager.html (read)
- Unity AudioSettings.GetDSPBufferSize(out bufferLength, out numBuffers) exists in 6.0. https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSettings.GetDSPBufferSize.html (read; the "above 20 ms perceptible" line in that summary is not used)
- Unity AudioSettings.OnAudioConfigurationChanged fires on device change (HDMI, USB headset) and on Reset(). https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSettings.OnAudioConfigurationChanged.html (read)
- Unity Time.realtimeSinceStartupAsDouble exists, double precision, ignores timeScale. https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Time-realtimeSinceStartupAsDouble.html (read)
- Unity Input System: InputEvent.time on the Time.realtimeSinceStartup timeline; default update mode runs input each frame before MonoBehaviour.Update; ProcessEventsInFixedUpdate associates events to the fixed slice by timestamp. https://docs.unity3d.com/Packages/com.unity.inputsystem@1.11/manual/Events.html (read). Update modes list. https://docs.unity3d.com/Packages/com.unity.inputsystem@1.11/manual/Settings.html (read). CallbackContext.time is the time the action was triggered, relative to realtimeSinceStartup, not necessarily the callback time. https://docs.unity3d.com/Packages/com.unity.inputsystem@1.11/api/UnityEngine.InputSystem.InputAction.CallbackContext.html (read)
- Unity Time settings page does NOT state default fixed timestep; the topic therefore says "50 Hz is 20 ms" as arithmetic, with no Unity default claimed. https://docs.unity3d.com/6000.0/Documentation/Manual/class-TimeManager.html (read)

## Platform audio
- Android Oboe low-latency guide: double buffering (buffer = 2 x burst; Oboe does this itself, AAudio default is higher), PerformanceMode LowLatency, OboeTester table: 20 ms all recommendations, 205 ms not low-latency mode, 26 ms not exclusive, 21 ms no output callback with MMAP, 62 ms no callback without MMAP, 53 ms buffer at maximum. https://developer.android.com/games/sdk/oboe/low-latency-audio (read)
- Oboe FullGuide: never block inside onAudioReady (allocation, file I/O, network, mutexes, sleep). https://github.com/google/oboe/blob/main/docs/FullGuide.md (read)
- Android low_latency feature flag 45 ms or less; pro 20 ms round trip; runtime estimates (Oboe calculateLatencyMillis, getTimestamp) miss delay the device does not know about (USB, HDMI, Bluetooth). https://developer.android.com/ndk/guides/audio/audio-latency (read; Oboe part taken from the sibling rhythm draft's sources; this session's fetch did not show the Bluetooth sentence, so the topic states it only as that draft did)
- Android measurement: round-trip latency by looping noise bursts through a full-duplex stream, loopback dongle for 3.5 mm and USB, OboeTester and CTS Verifier. https://source.android.com/docs/core/audio/latency/measure (read)
- Apple AVAudioSession.setPreferredIOBufferDuration: a request, check ioBufferDuration; typical max 0.093 s (4,096 frames at 44.1 kHz); minimum at least 0.005 s (256 frames), maybe lower. https://developer.apple.com/documentation/avfaudio/avaudiosession/setpreferrediobufferduration(_:) (read through Apple's JSON data endpoint of that page, https://developer.apple.com/tutorials/data/documentation/avfaudio/avaudiosession/setpreferrediobufferduration(_:).json)
- Web Audio look-ahead scheduling: setTimeout skewed by tens of ms or more; scheduler every 25 ms, look-ahead 100 ms, audio clock (currentTime) precise. https://web.dev/articles/audio-scheduling (read). The pattern is used in the topic as a design pattern; Unity and Godot equivalents are my mapping (Inference).
- NVIDIA PC latency stages (input-to-frame-start, frame-start-to-present, present-to-displayed; input sampling latency spread evenly across the sampling interval; no numbers given). https://developer.nvidia.com/blog/understanding-and-measuring-pc-latency/ (read)

## Arithmetic and inferences (no source says it)
- 1,024 / 48,000 = 21.3 ms; 256 frames at 44.1 kHz = 5.8 ms; 4,096 at 44.1 kHz = 92.9 ms. Arithmetic.
- 100 ppm x 180 s = 18 ms drift. The 100 ppm is an ASSUMED figure, labelled as such in the topic; real figures are not sourced. In practice the larger causes of drift are hitches, pauses and a late start; the topic says so.
- Polling once per frame adds 0 to one frame (0 to 16.7 ms at 60 Hz), average half a frame. Arithmetic, consistent with NVIDIA's "spread evenly" remark.
- 240 fps = 4.17 ms per camera frame. Arithmetic; the topic says the phone must really film at that rate.
- Unity dspTime is stepped by the mixer block. Inference from the documented definition (same as the sibling rhythm draft).
- Smoothing recipe (low-pass on the difference between clocks, 5 percent per frame) and the median-of-many-taps calibration (16 or more taps, drop first four and taps beyond about 150 ms): design advice, not from a source. The 5 percent gain in the snippet is untuned.
- Calibration includes the player's early-tap bias: relies on the sibling rhythm draft's treatment of negative mean asynchrony (Repp 2005, contested). https://link.springer.com/article/10.3758/BF03206433 (abstract only, via the sibling draft).
- Adriaensen, "Using a DLL to filter time" (delay-locked loop for timestamps of audio callbacks), https://kokkinizita.linuxaudio.org/papers/usingdll.pdf : NOT READ (the PDF text could not be decoded). Named in TECH only as "the reference I know of, not read here". Fact-checker: confirm the paper's subject or drop that sentence.
- Rock Band's separate audio and video calibration is cited in the sibling draft (https://www.harmonixmusic.com/blog/how-to-calibrate), not repeated here.
